# docs_tdd 系统复盘与优化计划

## 执行摘要

用户目标：**只给需求，系统自动完成从分支创建到提交的全流程，不漏需求、不卡死，兼顾效率与准确性**。

当前状态：v3.5 已大幅优化（产物减 95%，context 减 99%），但**小需求仍然消耗大量时间和 token，且仍有遗漏问题**。

核心矛盾：**为防遗漏而引入的保障机制（多层审查、门禁、规则加载）本身成为了效率瓶颈**。

## 一、当前系统状态评估

### 1.1 架构现状（v3.5）

**工作流**：
```
PRD → source normalization → 三阶段抽取（facts/requirements/surfaces）
  → 确定性 intake audit 
  → 独立覆盖审查（最多2轮，source-only 冷读）
  → 风险路由（V0/V1/V2）
  → V2 需人工 scope approval
  → safe work context + worktree 准备
  → 实现 + checkpoint
  → dev-check（非浏览器证据）
  → evidence runner（CLI-attested）
  → enforced verify（单一正式出口）
  → 有界修复（code/browser，各2轮）
  → delivery commit（不 push）
```

**已完成的优化**（从 CHANGELOG 和 baseline.json）：
- **产物压缩**：253 个流程文件 → 12 个（-95.26%）
- **Context 压缩**：342,592 字符 → 2,718 字符（-99.21%）
- **规则按需加载**：scene-based routing，brief 折叠
- **会话去重**：同 session 只返回 delta
- **确定性前置审计**：intake audit 在调用模型前拦截结构性错误
- **独立审查封顶**：最多 2 轮，避免无限循环
- **四项目 replay**：PR-02306/01930/02265 的遗漏问题做成回归夹具

### 1.2 历史遗漏问题分析

从 baseline.json 和项目 README：

| 项目 | 问题 | 根因 |
|------|------|------|
| PR-02265 | 提测后补 PRD amount/fee 语义 | 显式金额/费用语义被遗漏 |
| PR-02306 | 图片密码需求漏抽取 | PRD 含图片，抽取不完整 |
| PR-01930 | 集合第三入口漏 surface | 集合语义（"所有X"）的落点未完整映射 |

**系统应对**：
- v3.5 引入 source units（表格逐行归一化）
- 确定性 Coverage Compiler（要求每个 unit 必须处置）
- vnext-replay 夹具固化这些场景

### 1.3 效率问题分析

**Token 消耗来源**（推测，历史无完整记录）：

1. **多轮审查**：
   - 独立覆盖审查（source-only，最多 2 轮）
   - code review（G6 或 v2 verify）
   - 每轮都是完整模型调用

2. **规则加载**：
   - L1（~/.ai-rules/AGENT.md）：≤7K 字符
   - L2（.cursor/rules/*.mdc）：变化大
   - L3（rule-router.md + 场景包）：V0/V1 ≤4K，V2 ≤8K（目标，硬上限 24K）
   - 虽然已按需加载 + brief 折叠，但每次仍需注入

3. **验证循环**：
   - dev-check（实现期）
   - evidence runner（最终验证）
   - 有界修复（code 2轮 + browser 2轮）
   - 每次失败都可能触发新的 AI 调用

4. **小改动的"重型流程税"**：
   - 即使是单文件小改动，仍需走完整流程
   - V0（micro-change）虽然简化，但仍有 intake audit + 独立审查 + verify
   - 没有"快速通道"绕过审查

## 二、离用户预期的差距

### 2.1 预期 vs 实际对照表

| 预期目标 | 当前实现 | 差距 |
|---------|---------|-----|
| **只给需求** | ✅ PRD-only 输入已实现 | 0 |
| **安全建分支** | ✅ worktree + safe work context | 0 |
| **完整理解来源** | ⚠️ 独立审查 + intake audit，但仍有遗漏 | **中** |
| **只在必要时问** | ❌ V2 强制人工 scope approval；审查失败 escalate 人工 | **大** |
| **完成代码** | ✅ 可以完成 | 0 |
| **验证** | ✅ CLI-attested evidence | 0 |
| **修复** | ⚠️ 有界修复（各 2 轮），但超预算需人工 | **中** |
| **提交** | ✅ delivery commit（不 push）| 0 |
| **不漏需求** | ❌ 历史有 3 个遗漏案例，虽已做夹具 | **大** |
| **不卡死** | ⚠️ 有预算上限，但复杂需求可能卡在审查/修复循环 | **中** |
| **兼顾效率与准确性** | ❌ 小需求耗时长、token 多 | **大** |

### 2.2 关键问题

**问题 1：过度审查税**
- V2 需求即使很简单，也强制走人工 scope approval
- 独立覆盖审查对明显的小改动是浪费
- 示例：改一个文案、调整一个样式，也要走完整审查

**问题 2：漏需求仍然发生**
- 虽然有 intake audit + 独立审查，但 PR-02265/02306/01930 都是在这些机制上线后出的问题
- 说明：**结构化检查无法替代语义理解**
- AI 在抽取阶段就可能遗漏（"所有X"、图片需求、隐含语义）

**问题 3：小需求没有快速通道**
- V0 虽然简化了验证矩阵，但仍需：
  - intake audit
  - 独立审查（2 轮）
  - evidence runner
  - verify
- 一个改文案的需求，理想情况应该是：读 PRD → 改文件 → commit

**问题 4：反馈周期长**
- dev-check 只在"一批相关改动稳定后"运行
- 小步迭代时缺乏即时反馈
- 失败后才知道方向错了，已浪费 token

**问题 5：规则系统复杂度**
- 3 层规则（L1/L2/L3）
- 场景路由
- brief/compact/full 模式
- AI 需要理解这套系统本身就是负担

## 三、根因分析

### 3.1 为什么小需求慢？

**根本原因：系统为高风险、复杂需求设计，但对所有需求一视同仁**

```
系统设计假设：每个需求都可能遗漏 → 需要多层保障
实际情况：大部分需求很简单，遗漏风险低 → 保障机制成为负担
```

**类比**：
- 就像用 "坦克装甲" 保护所有人，即使只是去买菜
- 高风险场景（资金、权限）需要装甲
- 低风险场景（改文案）不需要

### 3.2 为什么仍然遗漏？【关键问题】

**用户洞察**：多轮审查很费时间效率低，而且审查了好几次还是有遗漏。**审查只是补救，不能本末倒置，应该提高第一次获取需求点的准确性。**

**根本原因：第一次抽取需求时理解不到位，后续审查无法弥补**

```
第一次理解错误 → 审查基于错误理解（GIGO）→ 实现基于错误理解 → 遗漏
```

#### 3.2.1 历史遗漏案例深度分析

| 项目 | 遗漏内容 | 第一次抽取时的问题 | 审查为何没发现 |
|------|---------|-------------------|--------------|
| **PR-02306** | 图片中的密码规则需求 | AI **没有深度解读图片**，只扫了一眼 | 审查也是基于 AI 的抽取结果，图片已"处理过"就没再看 |
| **PR-01930** | 集合的第3个入口 | AI 看到"所有入口"，但**没有完整枚举**，只找到2个就停了 | 审查检查"是否覆盖 source"，已抽取的2个都有映射，看起来"完整" |
| **PR-02265** | 显式 amount/fee 字段 | AI **注意力分散**，关键字段被淹没在大量细节中 | 审查检查结构完整性，但无法判断"语义重要性" |

**共同特征**：
1. **AI 的注意力问题**：扫过式阅读，而非精读
2. **缺乏完整性意识**："所有"没有完整枚举、图片没有深度解读
3. **审查的局限性**：只能检查"已抽取内容的结构"，无法发现"未抽取的遗漏"

#### 3.2.2 为什么第一次会理解错误？

**原因1：AI 注意力分散**
- 复杂 PRD（多页、多图、多表格）
- 一次性读完，信息过载
- 关键信息被淹没在细节中
- **类比**：让人一次性记住一本书的所有内容

**原因2：缺乏"完整性检查"思维**
- AI 是正向思考："这里有什么需求？"（发现）
- 缺少反向思考："我是否遗漏了什么？"（验证）
- 缺少边界思考："'所有'到底是哪些？"（枚举）
- **类比**：只问"包里有什么"，不问"购物清单上的都拿了吗"

**原因3：图片/表格处理不深入**
- 图片往往只看"有什么元素"
- 不深入理解"图片传达的需求是什么"
- 表格可能只看结构，不深入理解每行的语义
- **类比**：看设计稿只看颜色形状，不看交互逻辑

**原因4：缺乏领域知识引导**
- "资金"、"权限"、"不可逆操作"等高风险概念
- AI 可能当作普通文本，没有特殊关注
- 缺少领域特定的检查清单
- **类比**：医生看病历没有"ABCDE"急救检查法

**原因5：抽取过程太快**
- 当前流程：读 PRD → 一次性抽取 → 输出
- 没有"思考 → 验证 → 确认"的循环
- 没有分阶段、分主题的深入理解
- **类比**：考试时匆匆答题，没有检查

#### 3.2.3 审查为什么无法弥补？

**结构化检查的局限**：
1. **Intake audit**：只检查结构（重复 ID、表格行锚定），无法理解语义
2. **Coverage review**：检查"已抽取内容是否覆盖 source units"，但：
   - 如果第一次就没理解图片，审查也不会重新深度解读
   - 如果第一次没完整枚举"所有X"，审查也不知道漏了哪个
   - **只能发现"已抽取内容"的问题，无法发现"未抽取"的遗漏**

**独立审查的悖论**：
- 审查是 source-only 冷读，看的是 AI 第一次抽取的结果
- 如果第一次理解就错了，审查也基于错误理解
- **GIGO（Garbage In, Garbage Out）**

**多轮审查的边际收益递减**：
- 第 1 轮：可能发现明显结构问题
- 第 2 轮：如果仍是相同理解，很难发现新问题
- 继续增加轮次：只是浪费 token，不解决根本问题

### 3.3 为什么 AI 变慢？

**推测原因**（需验证）：

1. **规则负担**：
   - 即使已压缩，每次仍需加载 L1+L2+L3
   - AI 需要理解规则体系本身
   - 思考时间增加

2. **流程负担**：
   - 需要理解 work-item 结构
   - 需要填写 checkpoint/surfaces
   - 需要调用各种 CLI 命令
   - 心智负担大

3. **保守策略**：
   - 为避免遗漏，AI 倾向于过度仔细
   - 小改动也反复确认
   - 增加不必要的来回

## 四、优化方向

### 4.1 核心策略双管齐下

**策略 1：提高第一次理解的准确性（治本）** ⭐️ 【用户强调：优先级最高】
- **目标**：第一次就把需求理解对、抓全，不依赖后续审查补救
- **本末倒置的问题**：当前系统花大量时间在多轮审查上，但第一次理解错了，审查再多也是在错误基础上修修补补

**策略 2：分级处理，简化流程（提效）**
- 简单需求走快速通道
- 复杂需求保留必要保障

### 4.2 核心优化：第一次就理解准确【重点】

#### 4.2.1 整体思路

**从"快速扫描"改为"精读 + 自我验证"**

```
当前流程（问题）：
  读 PRD → 一次性抽取 → 输出 → 审查发现问题 → 返工

优化流程（目标）：
  深度精读 → 分主题抽取 → 自我完整性检查 → 高质量输出 → (审查变成可选)
```

**关键原则**：
1. **慢即是快**：第一次花 2 倍时间精读，避免后续 3-5 轮返工
2. **主动验证**：不等审查发现问题，AI 自己检查完整性
3. **强制枚举**：遇到"所有"、"每个"等关键词，必须完整列举
4. **深度解读**：图片、表格不能浅尝辄止，要深入理解

#### 4.2.2 具体机制

**机制 1：多遍精读法（Multi-Pass Reading）**

**第 1 遍：全局扫描（5 分钟）**
```
目标：建立整体认知地图
- 这是什么类型的需求？（新功能/修改/bug修复）
- 涉及哪些模块？（前端/后端/数据库）
- 主要用户流程是什么？
- 风险等级如何？（V0/V1/V2）
- 有哪些富媒体？（图片/表格/流程图）

输出：需求概要（100-200字）
```

**第 2 遍：分主题深入理解（按重要性排序）**
```
优先级 1（高风险要素）：
  - 资金相关：金额、费用、充值、提现、支付
  - 权限相关：登录、注册、角色、访问控制
  - 不可逆操作：删除、下线、禁用
  - 数据修改：创建、更新、批量操作
  → 每个都要：明确范围、边界条件、异常处理

优先级 2（功能完整性）：
  - 页面/组件：每个页面的完整元素
  - 接口/字段：每个接口的完整字段
  - 状态流转：每个状态的完整路径
  - 集合语义："所有"、"每个"的完整枚举
  → 列清单，逐项确认

优先级 3（交互细节）：
  - 按钮、输入框、文案
  - 提示、错误信息
  - 加载、空状态
  → 快速扫描，重点关注特殊说明
```

**第 3 遍：富媒体深度解读**
```
图片（每张都要）：
  1. 这是什么类型？（界面截图/流程图/示意图）
  2. 传达了什么需求？（不是"有什么元素"，而是"要实现什么"）
  3. 有哪些关键信息？（规则、条件、交互）
  4. PRD 文字中是否已覆盖？（如果图片有、文字没有 → 标记为关键）
  
  示例（PR-02306）：
  - 图片显示密码规则：8-20位、必须包含字母+数字
  - 文字中只说"密码校验"，没有具体规则
  - → 图片中的规则是关键需求，必须抽取

表格（每行都要）：
  1. 表格传达什么？（字段列表/状态流转/权限矩阵）
  2. 每一行的语义是什么？
  3. 有没有隐含的规则？（必填/可选、依赖关系）
  4. 特殊行是否需要特殊处理？
```

**第 4 遍：完整性自检（关键！）**
```
反向检查（从 PRD 到抽取）：
  ✓ PRD 中的每个关键词是否都被处理？
  ✓ 每张图片是否都被深度解读？
  ✓ 每个表格的每一行是否都有映射？

正向检查（从抽取到 PRD）：
  ✓ 每条需求是否都能在 PRD 中找到依据？
  ✓ 每个 surface 是否都能对应到具体落点？

边界检查：
  ✓ "所有X"：X 到底有哪些？是否完整枚举？
  ✓ "每个Y"：Y 到底有哪些？是否遗漏？
  ✓ "相关Z"：相关的范围是什么？是否明确？

高风险检查（如果是 V2）：
  ✓ 资金操作：金额计算、余额检查、不可逆确认 ✓
  ✓ 权限操作：谁能访问、谁能修改、审计日志 ✓
  ✓ 数据修改：修改范围、影响面、回滚方案 ✓
```

**机制 2：强制枚举协议（Mandatory Enumeration）**

**触发条件**：PRD 中出现以下关键词
- "所有"、"全部"、"每个"、"各"
- "相关"、"涉及"（范围模糊）
- "等"、"..."（列举不完整）

**执行协议**：
```
步骤 1：识别枚举目标
  PRD："修改所有登录入口的密码规则"
  → 枚举目标：登录入口

步骤 2：完整枚举（不能偷懒）
  方法 1：从 PRD 中寻找线索
  方法 2：从代码仓库中搜索（grep "login"）
  方法 3：从业务常识推断（账号密码、手机号、邮箱、第三方）
  
  输出：
  1. 账号密码登录（主入口）
  2. 手机号验证码登录
  3. 第三方登录（微信、Google）
  
步骤 3：验证完整性
  问自己：还有其他登录入口吗？
  - 忘记密码流程？（算，也要改）
  - 注册流程？（算，密码规则相同）
  - SSO 单点登录？（不算，企业版功能）
  
步骤 4：在抽取中明确标记
  Requirement R-001: 修改密码校验规则（覆盖 3 个入口 + 2 个流程）
  Surface S-001: 账号密码登录页（apps/web/Login.tsx）
  Surface S-002: 手机号登录页（apps/web/PhoneLogin.tsx）
  Surface S-003: 第三方登录回调（apps/web/OAuth.tsx）
  Surface S-004: 忘记密码页（apps/web/ResetPassword.tsx）
  Surface S-005: 注册页（apps/web/Register.tsx）
  
  → 5 个落点，都要改，一个不能漏
```

**反面案例（PR-01930）**：
```
PRD："修改所有入口"
AI 第一次抽取：找到 2 个入口就停了
审查：2 个入口都有映射，看起来"完整"
实现：只改了 2 个
提测：发现第 3 个入口没改 ❌

根因：AI 没有执行"强制枚举"，看到 2 个就以为"所有"
```

**机制 3：图片深度解读协议（Deep Image Understanding）**

**不合格的图片处理**：
```
AI：这是一张登录页截图，包含用户名输入框、密码输入框、登录按钮。
→ 只描述了元素，没有提取需求
```

**合格的图片处理**：
```
AI：图片显示登录页，需要抽取以下需求：

R-IMG-001（从图片文字提取）：
  密码输入框下方的提示文字："8-20位，必须包含字母和数字"
  → 需求：密码长度 8-20，必须字母+数字组合
  → PRD 文字中未提及此规则 ⚠️
  → 标记为【图片独有需求】，优先级：高

R-IMG-002（从图片交互提取）：
  密码输入框右侧有"眼睛图标"
  → 需求：密码可见/隐藏切换功能
  → PRD 文字中提到"密码输入"，但未说明可见性切换
  → 标记为【图片补充需求】，优先级：中

R-IMG-003（从图片样式提取）：
  登录按钮为蓝色，圆角 4px
  → 需求：按钮样式（如果是设计稿）
  → PRD 是功能需求，样式参考 Figma
  → 标记为【样式参考】，优先级：低（Figma 阶段处理）
```

**深度解读清单**：
```
对每张图片问 5 个问题：
1. 图片类型？（界面/流程/示意图）
2. 传达什么需求？（不是"有什么"，是"要做什么"）
3. 哪些信息是文字中没有的？（图片独有 → 高优先级）
4. 哪些细节容易被忽略？（小字、边角、状态）
5. 如果我不看这张图，会漏掉什么？（完整性验证）
```

**机制 4：领域检查清单（Domain Checklist）**

**根据需求类型，自动激活对应检查清单**

**资金类需求检查清单**：
```
□ 金额字段：类型（整数/小数）、单位（元/分）、精度
□ 余额检查：充值/扣减前是否检查余额充足
□ 不可逆确认：是否有二次确认弹窗
□ 异常处理：余额不足、支付失败、超时如何处理
□ 审计日志：是否记录操作人、时间、金额、原因
□ 并发控制：是否有防重复扣款机制
□ 展示规则：金额格式化、货币符号、千分位
```

**权限类需求检查清单**：
```
□ 角色定义：哪些角色可以访问
□ 权限校验：前端隐藏 + 后端校验（双重）
□ 敏感操作：是否需要二次验证（密码/验证码）
□ 审计日志：谁在什么时间访问了什么
□ 越权测试：是否考虑越权访问场景
□ Token 刷新：长时间操作是否需要刷新登录态
```

**列表/表格类需求检查清单**：
```
□ 数据来源：接口是什么、字段映射
□ 分页：前端分页/后端分页、每页条数
□ 排序：默认排序、可排序字段
□ 筛选：筛选条件、多条件组合逻辑
□ 搜索：搜索字段、模糊/精确匹配
□ 空状态：无数据时的展示
□ 加载状态：首次加载、翻页加载
□ 错误状态：接口失败时的展示
□ 操作列：编辑/删除/详情等按钮
□ 批量操作：是否支持、如何实现
```

**表单类需求检查清单**：
```
□ 字段列表：每个字段的类型、必填/可选、默认值
□ 校验规则：前端校验 + 后端校验
□ 错误提示：每个字段的错误提示文案
□ 联动关系：字段之间的依赖关系
□ 提交逻辑：成功后跳转/提示、失败后如何处理
□ 编辑回填：编辑时如何获取初始值
□ 防重复提交：是否需要
```

**机制 5：抽取后的自我验证环节（Self-Verification）**

**AI 完成抽取后，不直接输出，而是先自我审查**

```
Step 1：完整性自检
  问自己：
  - PRD 中的关键词是否都被处理？
  - 图片是否都被深度解读？
  - "所有X"是否都被完整枚举？
  - 高风险点（资金/权限）是否都被覆盖？
  
  方法：生成"自检报告"（内部文档，不给用户）
  
  示例：
  ✓ PRD 提到"所有登录入口"，已枚举 5 个入口
  ✓ 图片 3 张，已深度解读，提取 7 条需求
  ⚠️ PRD 提到"相关页面"，范围不明确 → 需要枚举
  ✓ 涉及资金扣减，已覆盖余额检查、二次确认、审计日志

Step 2：逻辑一致性检查
  - Requirements 和 Surfaces 是否对应？
  - 是否有需求没有落点？
  - 是否有落点没有需求？
  
Step 3：高风险复核
  如果是 V2 需求：
  - 对照领域检查清单，逐项确认
  - 生成"高风险点清单"
  
Step 4：输出质量评分
  给自己的抽取打分（内部）：
  - 完整性：9/10（"相关页面"范围待明确）
  - 准确性：10/10
  - 深度：9/10（图片 2 的交互细节可以更深入）
  
  如果评分 < 8，重新精读相关部分
```

**机制 6：用户快速确认环节（10 秒检查）**

**AI 完成自我验证后，生成面向用户的"理解摘要"**

```
格式：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
需求理解摘要（请确认是否遗漏）

【核心功能】
- 修改密码校验规则：8-20位，必须字母+数字
- 涉及 5 个入口：账号密码登录、手机号登录、第三方登录、忘记密码、注册

【关键落点】
- Login.tsx、PhoneLogin.tsx、OAuth.tsx、ResetPassword.tsx、Register.tsx
- 共享校验逻辑：新增 validatePassword() 工具函数

【高风险点】
- 无（纯前端校验，无资金/权限操作）

【图片独有需求】
- 密码可见/隐藏切换（图片 1 显示眼睛图标）

【待确认】
- PRD 提到"相关页面"，是否还包括其他页面？

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
请确认：✅ 理解正确 / ⚠️ 有遗漏（请指出）
```

**用户只需 10 秒扫一眼**：
- ✅ 看起来对 → 继续
- ⚠️ 有问题 → 立即纠正（成本：10 秒，收益：避免返工）

**对比当前流程**：
```
当前：
  抽取 → 审查 → 发现问题 → 返工 → 再审查
  用户介入时间：实现后的提测阶段
  返工成本：高（已经写了代码）

优化后：
  抽取 → 自我验证 → 用户快速确认（10秒）→ 实现
  用户介入时间：抽取后立即
  返工成本：低（还没写代码）
```

#### 4.2.3 机制落地方案

**方案 A：Prompt Engineering（快速，推荐先试）**

在 `vnext-extract.mjs` 的 AI prompt 中加入：

```
# 需求抽取指南 v2.0（精读版）

你的任务是精确、完整地理解需求。多轮审查很费时且效率低，即使审查多次仍可能遗漏。
**关键原则：第一次就理解准确，不依赖后续审查补救**。

## 抽取流程（强制遵循）

### 第 1 步：全局扫描（5 分钟，不要跳过）
快速阅读全文，回答：
- 需求类型？（新功能/修改/bug修复）
- 涉及模块？（前端/后端/数据）
- 风险等级？（资金/权限/不可逆 → V2；多影响面 → V1；局部微改 → V0）
- 富媒体？（图片、表格、流程图的数量和类型）

生成需求概要（100-200 字）。

### 第 2 步：分主题深入理解（按优先级）

**优先级 1：高风险要素（如果有）**
关键词：资金、金额、费用、充值、提现、支付、权限、登录、删除、禁用
→ 每个都要明确：范围、边界、异常处理、审计

**优先级 2：完整性关键词（强制枚举）**
遇到以下词必须完整列举，不能遗漏：
- "所有"、"全部"、"每个"、"各"
- "相关"、"涉及"（范围模糊，需要明确）

示例：
  PRD："修改所有登录入口"
  → 必须枚举：账号密码、手机号、邮箱、第三方、忘记密码、注册
  → 在代码中搜索确认：grep -r "login" 
  → 输出：5 个入口（明确列出）

**优先级 3：富媒体深度解读（每个都要）**

图片（每张）：
- 不是描述"有什么元素"，而是"传达什么需求"
- 重点：图片中的文字、规则、交互、状态
- 标记：哪些是文字中没有的（图片独有需求）

示例（PR-02306 教训）：
  图片显示密码输入框下方提示："8-20位，必须包含字母和数字"
  → 这是需求！不是装饰！
  → 文字中只说"密码校验"，没有具体规则
  → 必须抽取：R-IMG-001: 密码长度 8-20，必须字母+数字

表格（每行）：
- 确认表格类型（字段列表/状态流转/权限矩阵）
- 逐行理解语义
- 注意隐含规则（必填/可选、依赖）

### 第 3 步：自我完整性检查（强制，不要跳过）

反向检查（从 PRD 到抽取）：
□ PRD 每个关键词是否都处理了？
□ 每张图片是否都深度解读了？
□ 每个表格的每一行是否都映射了？

正向检查（从抽取到 PRD）：
□ 每条需求能否在 PRD 中找到依据？
□ 每个 Surface 能否对应到具体落点？

边界检查（针对集合语义）：
□ "所有 X"：X 有哪些？是否完整枚举？（代码搜索确认）
□ "每个 Y"：Y 有哪些？是否遗漏？
□ "相关 Z"：相关的范围是什么？是否明确？

高风险检查（如果是 V2）：
□ 资金：金额计算、余额检查、二次确认、审计日志
□ 权限：访问控制、敏感操作、审计
□ 数据：修改范围、影响面、回滚

### 第 4 步：输出质量自评

给自己的抽取打分：
- 完整性：__/10（是否有遗漏？）
- 准确性：__/10（理解是否正确？）
- 深度：__/10（图片/表格是否深入？）

如果任一项 < 8，重新精读相关部分。

### 第 5 步：生成理解摘要（给用户确认）

格式：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
需求理解摘要

【核心功能】（3-5 条，一句话概括）
- ...

【关键落点】（代码文件/组件）
- ...

【高风险点】（如果有）
- ...

【图片独有需求】（文字中没有，但图片有的）
- ...

【待确认】（范围不明确的）
- ...

━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 历史遗漏教训（必读）

案例 1：PR-02306
  问题：图片中的密码规则（8-20位、字母+数字）被遗漏
  根因：只看了图片的布局，没有读图片中的文字
  教训：图片中的文字是需求，不是装饰

案例 2：PR-01930
  问题："所有入口"只找到 2 个，漏了第 3 个
  根因：看到 2 个就停了，没有完整枚举
  教训：遇到"所有"必须完整枚举，代码中搜索确认

案例 3：PR-02265
  问题：显式 amount/fee 字段被遗漏
  根因：关键字段被淹没在大量细节中
  教训：资金相关必须用检查清单逐项确认
```

### 4.3 次要优化：流程简化（配合第一次理解准确）

**前提**：只有当第一次理解准确率达到 95%+ 时，才能简化后续审查

#### 4.3.1 【高优先级】快速通道（Lite Path）

**目标**：单文件、低风险改动在 2 分钟内完成

**适用场景**：
- 纯文案修改（i18n key 不变）
- 单一样式调整（无行为变化）
- 简单 bug 修复（单函数，无依赖变化）
- 明确的小增强（单一明确落点）

**流程**：
```
PRD → 快速理解（AI 自评风险）→ 
  → 低风险？
    YES → 直接实现 → 定向测试 → commit
    NO  → 转标准流程
```

**关键差异**：
- **跳过独立审查**：AI 直接理解 PRD，不走三阶段抽取
- **跳过 V2 人工确认**：系统自动判定为 V0-lite
- **最小验证**：只跑相关文件的 lint + 定向测试
- **即时反馈**：改完立即验证，不等"一批稳定"

**安全措施**：
- AI 必须显式声明"这是低风险快速通道"
- 如果判断错误，事后降级到标准流程
- 保留完整 audit trail

#### 4.2.2 【高优先级】智能提问策略

**当前问题**：
- V2 所有需求强制人工 scope approval
- 审查失败 escalate 人工
- 过度依赖人工

**优化**：
```
V2 scope approval 改为：
  - 系统先自评：风险信号是否明确？
  - 明确（funds/permission/irreversible）→ 必须人工确认
  - 不明确（只是因为 multi-surface）→ 提供摘要，允许 AI 继续，但标记"需事后复核"
```

**审查失败改为**：
```
  - 第 1 次 changes-required → AI 自动修正，不问人
  - 第 2 次相同 finding → escalate，但同时提供"AI 建议方案"
  - 人只需选择：接受 AI 方案 / 提供新方向 / 延期
```

#### 4.2.3 【中优先级】理解质量前置

**当前问题**：抽取阶段的理解错误，后续无法纠正

**优化**：
1. **增加"理解确认"环节**（针对复杂需求）：
   ```
   AI 完成抽取后 → 生成"需求理解摘要"（人类可读）→ 
     用户快速扫一眼（10 秒）→ 
     OK 继续 / 指出遗漏
   ```

2. **利用历史遗漏模式**：
   - 把 PR-02265/02306/01930 的遗漏模式固化为"检查清单"
   - AI 抽取时主动检查：
     - 是否有"所有X"、"每个Y"等集合语义？
     - 是否有图片？图片中的关键信息是否抽取？
     - 是否有金额/费用相关？是否明确处理？

3. **双 AI 交叉验证**（针对 V2）：
   - Agent 1 抽取需求
   - Agent 2 独立读 PRD，检查 Agent 1 是否遗漏
   - 只标记差异，不重复抽取

#### 4.2.4 【中优先级】渐进式验证

**当前问题**：dev-check 要等"一批稳定"，反馈慢

**优化**：
1. **编辑后即时轻量检查**（IDE 级别）：
   - Lint 受影响文件
   - 类型检查受影响文件
   - 不跑测试，不写状态文件

2. **checkpoint 时中等检查**：
   - Lint + 类型检查
   - 相关单测
   - 写 checkpoint，但标记"partial"

3. **verify 时完整检查**：
   - 全部证据命令
   - 写正式 result

#### 4.2.5 【低优先级】规则系统简化

**长期方向**：
- L1/L2/L3 对 AI 来说太复杂
- 考虑：AI 只看"当前任务需要知道的规则"
- 规则注入由系统智能决策，AI 无感

**短期**：
- 优化 brief 模式，进一步压缩
- 常用规则直接 bake 进 AI prompt，不每次传

### 4.3 优先级排序

**Phase 1（立即）**：
1. ✅ 快速通道（Lite Path）- 解决"小改动慢"
2. ✅ 智能提问策略 - 减少不必要的人工介入

**Phase 2（1-2 周）**：
3. ✅ 理解质量前置 - 减少遗漏
4. ✅ 渐进式验证 - 加快反馈

**Phase 3（1-2 月）**：
5. ⏸ 规则系统简化 - 降低心智负担

## 六、风险与缓解

### 6.1 风险

**风险 1：快速通道误判风险**
- 低风险判断错误，实际是高风险
- 缓解：
  - 保守判断（有疑问就走标准流程）
  - 事后审计（定期检查快速通道的改动质量）
  - 明确白名单（文案、样式调整等明确场景）

**风险 2：减少审查导致遗漏增加**
- 跳过独立审查可能增加遗漏
- 缓解：
  - 只在明确低风险场景跳过
  - 增加理解确认环节补偿
  - 保留 V1/V2 的完整审查

**风险 3：系统复杂度增加**
- 增加快速通道等机制，系统更复杂
- 缓解：
  - 对用户透明（自动判断）
  - 清晰的分层逻辑
  - 完整的测试覆盖

## 九、风险与缓解

### 9.1 Phase 1 风险

**风险 1：精读导致抽取时间过长**
- 预期：5 分钟 → 10 分钟
- 缓解：总体仍然更快（避免返工）
- 监控：如果超过 15 分钟，优化 prompt

- 缓解：
  - 格式简洁，10 秒能确认
  - 可选确认，不阻塞流程
  - 只在遗漏风险高时强制确认（V2）

**风险 3：检查清单覆盖不全**
- 缓解：
  - 从历史案例提炼
  - 持续迭代补充
  - 用户可自定义检查清单

### 9.2 整体风险

**风险 4：Prompt 过长影响 AI 理解**
- 当前 prompt 可能已经很长
- 增加精读指令可能超过最佳长度
- 缓解：
  - 精简其他部分
  - 分阶段注入（第一次简洁，发现问题时再注入详细指令）

**风险 5：不同 AI 模型效果差异**
- Prompt Engineering 在 Claude 上有效，Pi 上可能不同
- 缓解：
  - 分别测试
  - 必要时分模型定制 prompt

## 十、结论

### 10.1 核心洞察

**用户的关键洞察**："多轮审查很费时间效率低，而且审查了好几次还是有遗漏。应该提高第一次获取需求点的准确性，尽量一次就成功。后面的审查只能是补救，不能本末倒置。"

**完全正确！** 当前系统的问题：
- ❌ 把希望寄托在"多轮审查"上
- ❌ 第一次理解草率，指望后续补救
- ❌ 审查是结构化检查，无法发现语义遗漏
- ❌ GIGO（Garbage In, Garbage Out）

### 10.2 优化策略

**治本（最高优先级）**：第一次就理解准确
1. 多遍精读法（4 遍扫描）
2. 强制枚举协议（遇到"所有"必须枚举）
3. 图片深度解读（提取需求，不只描述元素）
4. 自我完整性检查（4 个维度）
5. 领域检查清单（自动激活）
6. 理解摘要确认（用户 10 秒检查）

**治标（配合优化）**：流程简化
- 快速通道（低风险需求）
- 智能提问（减少人工介入）
- 渐进式验证（加快反馈）

### 10.3 预期效果

**Phase 1（治本）**：
- 第一次准确率：60-70% → **90-95%**
- 遗漏率：5-10% → **1-2%**
- 审查返工：2-3 次 → **0-1 次**
- 总体耗时：**-30-40%**（虽然抽取时间 +100%，但返工 -70%）

**Phase 2-5（治标）**：
- 小需求耗时：**-85%**
- Token 消耗：**-80%**
- 人工介入：**-70%**

### 10.4 实施优先级

**立即开始（1-2 天）**：
1. ⭐️ **优化抽取 Prompt**（多遍精读、强制枚举、图片深度解读）
2. ⭐️ **增加理解摘要**（用户 10 秒确认）
3. ⭐️ **领域检查清单**（自动激活）

**1 周后评估**：
- 如果准确率 > 90%，继续 Phase 3-5（流程简化）
- 如果准确率 < 90%，实施双 Agent 交叉验证

**1 个月后**：
- 系统整体优化完成
- 达到用户预期的 80-90%

### 10.5 不完美但务实

**承认局限**：
- 无法做到 100% 零遗漏（AI 理解本身有限制）
- 复杂需求仍需人工判断
- 但可以做到：
  - 80% 的简单需求快速完成
  - 95%+ 的需求第一次就理解对
  - 遗漏率 < 2%
  - 用户感受"系统基本达到预期"

**当前系统已经很好，但过于"重装甲"**：
- ✅ 架构合理、机制完善
- ✅ 已大幅优化（产物 -95%，context -99%）
- ❌ 对所有需求一视同仁，小需求负担重
- ❌ 结构化检查无法覆盖语义理解
- ❌ 过度依赖人工介入

**核心策略：分级处理**
- 简单的事情简单做（快速通道）
- 复杂的事情慎重做（保留完整流程）
- 提前发现理解错误（理解确认 + 遗漏模式检查）
- 减少不必要的人工（智能提问）

**预期：达到用户目标的 80-90%**
- 小需求：2-5 分钟完成（vs 当前 15-30 分钟）
- 遗漏率：<2%（vs 当前 ~5-10%）
- 人工介入：0-1 次（vs 当前 2-3 次）
- 保持高风险场景的严格保障

**不完美，但务实**：
- 无法做到 100% 零遗漏（AI 本身的理解限制）
- 无法让所有需求都"一键完成"（复杂需求需要人工判断）
- 但可以让 80% 的简单需求快速完成，同时保持质量
