全景 · Overview

一个工作，三个抓手

三项优化都指向同一个问题：规则多、放得乱、加载贵、执行靠自觉。分别从「架构表达」「分层归属」「加载成本」三个切面根治。

01

组件到 API 架构规则

把含混的单链重构为「调用链 + 数据链」双向表达，配五层契约表、设计前置模板与机器兜底扫描——架构从口号变门禁。

共享内核 + 三个薄适配器 + 一个执行器 + 一份指纹证据，让 Codex / Claude / Cursor 吃同一份规则，唯一判据定落层。

03

AI 内存与 Token 规划

三级按需加载 + 确定性缓存 + 持久记忆，让每次读取只服务当前决策——省 Token 不降质量。

① 组件到 API 架构规则 · 问题

架构是「文档口号」，落不成约束

  • 表述含混：Page → hook → schema/mapper → API 把「调用方向」和「数据返回方向」混为一谈，最误导的是让人以为 Mapper 会去调 API。
  • 缺层间契约：没有一张规定每层「输入/输出/允许依赖/禁止依赖」的表，组件直连 DTO、Service 反向依赖 UI 等违例无据可依。
  • 规则加载不确定：写数据请求 UI 或 Query Hook 时，该读的分层规则不会被自动路由到。
  • 设计阶段无前置：技术方案不要求编码前登记完整数据链，问题拖到写码甚至 review 才暴露。
  • 静态检查太弱：旧 CODE-ARCH-001 只能抓 .tsx 里的 fetch()，抓不到 Hook 直连请求、组件 import DTO、Mapper 反向依赖等结构性问题。
① 组件到 API 架构规则 · 方案

双向链路 + 五层契约 + 三道关卡

重构表达
  • 单链拆为调用链与数据链两条（api-and-mapper.md §1）
  • 五层契约表：Component / Query Hook / API Service / Schema / Mapper 各自输入·输出·允许/禁止依赖
  • 明确 Mapper 为无网络、无状态、无 UI 依赖的纯转换层
左移到设计
  • 技术方案模板升级 v3：请求型功能 G4 前必须登记完整数据链表
  • 新增门禁 DOC-G4-006/007，仅约束 v3、不回溯阻断存量
  • 纯 UI 可写带来源说明的 N/A
机器兜底
  • 新增 CODE-ARCH-003（warn-first）：changed-file import 扫描
  • 提示 Mapper 反依赖、组件穿透 Hook、Service 依赖 UI、生产链引入 fixture
  • 路由新增 write_query_hook，写数据 UI/Hook 自动加载分层规则

② 统一管理 coding 规则 · 问题

三个工具、三处地方，规则各说各话

  • 多处重复维护：同一规则在多个文件重复，改一份、其余漂移。
  • 该放哪一层无唯一判据：纯手艺、FameEX 锚点、流程门禁混在一起，「错层」等同漏继承。
  • 三个 Agent 吃的规则不一致：Codex 集成最好；Claude 只模糊提一句 docs_tdd、无 gate；Cursor 的 ~/.cursor/rules 是空的。
  • 副本已实际漂移：Codex 与 Claude 的 coding-quality、figma-read skill SHA-256 已不一致。
  • 「被执行」无法证明：旧指纹只覆盖 L3，证明不了实际消费了哪个版本的 L1/L2/适配器。
  • 个人规则易污染团队：试验规则一旦写进 tracked 文件就影响同事。
② 统一管理 coding 规则 · 方案

共享内核 + 薄适配器 + 执行器 + 指纹证据

分层判据唯一真值源 = rule-inheritance.md §0：纯手艺→L1，带 FameEX 锚点→L2，流程门禁→L3；一条规则只落一层，其余层只放指针。

L1 纯手艺
  • 唯一源 ~/.ai-rules/AGENT.md + skills
  • Codex / Claude 经 symlink 消费同一份，副本漂移归零
L2 仓库锚点
  • .cursor/rules/*.mdc（~80 个，glob 触发）
  • 团队影响面，本轮只诊断不改，冲突仅 WARN
L3 流程门禁
  • docs_tdd/ 被 .git/info/exclude 本地排除
  • router / inheritance / execution-model + Cursor 用户级适配器

执行器：docs-tdd.mjs（新增 doctor）+ effective-rules.mjs（L1+适配器+L2+L3 一起打「effective 指纹」）+ 幂等安装脚本 + Claude PostToolUse hook。

③ AI 内存与 Token 规划 · 问题

上下文越滚越重，命中即全量加载

  • 常驻规则挤占预算：rule-router.md 曾达 4855 / 8000 字符，占去大半常驻窗口。
  • 命中即全量：一个场景命中就要读整篇专题（architecture-and-state.md 24.8K、rule-ids-and-gates.md 23.2K），大量正文与当前任务无关。
  • 重复执行：changed/gate 每次全量重跑；只有文件缓存，模型每轮仍要重新消费全文。
  • 跨会话记忆丢失：AI 无持久记忆，反复解释同一背景、踩同一坑（意译文案、gate 假阳性）。
  • 会话内存高：长对话 + 图片 + 工具输出持续累积（Codex 桌面进程可达 ~1.11 GB），单压 Markdown 解决不了。
③ AI 内存与 Token 规划 · 方案

三级按需加载 + 确定性缓存 + 持久记忆

三级加载
  • L0 常驻：rule-router.md，命中才读正文
  • L1 场景包：context 默认 --compact，只摘录指定章节
  • L2 全文：仅歧义或 gate 失败时 --full
确定性缓存
  • 章节级路由：大文档按 "sections":"1-3" 加载
  • 增量缓存 PASS-only：key 含 release + diff + 文件 hash
  • 规则一变即失效；--write/失败永远真跑
持久记忆
  • MEMORY.md 索引 + ~28 条主题记忆
  • 事实/决定/踩坑沉淀，跨会话不再重述
  • 摘要收敛：项目 summary 目标 1800 / 硬限 2200

红线：不为省 Token 跳过 PRD 图片/表格/schema/视觉验收；compact 严格按 rule-index.json 章节生成、带 source hash，拒绝有损的 AI 临时总结——Markdown 仍是唯一真值。
