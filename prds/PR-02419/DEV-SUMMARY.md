# PR-02419 开发摘要

> **目的**：为 AI 提供精准导航，避免全量读 PRD。人工维护，5-10 分钟完成。

---

## 一句话需求

运营后台修改用户类型时，前端校验 + 拦截公司做市用户，后端独立二次校验。

---

## 架构决策

### 前后端分工
- **前端**：提交前校验账户类型，命中则 Toast 拦截，不发请求
- **后端**：接口写入前独立校验，命中则拒绝并返回错误码（前端不能绕过）
- **识别依据**：用户的"账户类型"字段（accountType），值为"公司做市用户"时命中

### 影响范围（重要！）
- **apps/admin** 3 个页面/场景：
  1. 用户详情页 → 修改用户类型
  2. 用户列表 → 批量设置类型
  3. 用户批量管理 → 批量设置类型
- **不改 apps/web**（C 端无此功能）
- **不改 apps/h5**（移动端无此功能）

---

## 技术锚点

### 业务规则（§4.1.1）
1. **触发时机**：点"确认"按钮时
2. **校验对象**：本次被修改的用户（单个或批量）
3. **识别方式**：读用户当前的"账户类型"字段
4. **命中拦截**：
   - 单个修改：Toast 提示"该用户为公司做市用户，禁止修改用户类型"，不提交请求
   - 批量修改：部分命中则部分失败，Toast 提示失败的 UID 列表："111111111, 222222222 修改失败"
5. **未命中**：继续现有流程，不做额外处理

### 页面反馈文案（§4.1.2）
- PRD 里有个表格 `<sheet sheet-id="Nd1i1f">`，**需要读取这个表格获取完整文案**
- 初步已知：Toast 文案 = "该用户为公司做市用户，禁止修改用户类型"

### 后端接口（§4.2）
- **接口自带校验**：后端会在写入前独立校验，前端无需关心实现
- **前端要处理的错误码**：见 PRD §4.2.2（需要读取确认错误码 → Toast 文案的映射）
- **并发问题**：后端处理，前端不管
