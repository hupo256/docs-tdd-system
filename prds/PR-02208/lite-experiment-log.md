## 实施过程

### 发现的问题

**1. Lite 模式提炼清单不完善**
   - 影响：新增页面类需求缺少"页面位置"提炼项
   - 解决方案：增强清单，增加"新增页面/组件"专项检查

**2. 人工提炼容易遗漏技术细节**
   - 影响：只关注"做什么"，忽略"放在哪"
   - 解决方案：提供原型图信息提取检查表（路由、菜单、面包屑、标题）

**3. API 依赖严重性标记不明确**
   - 影响：标记了"需要 API"但没有标记"硬阻塞"
   - 解决方案：在 work-item 模板中明确区分：可选 / 软依赖 / 硬阻塞

**4. 适用场景判断不够精准**
   - 影响：复杂度较高的需求（新增页面 + API 依赖）被误判为适合 lite
   - 解决方案：增加 lite 模式前置检查清单

### 意外情况

**1. 15 分钟调研后仍未找到目标代码**
   - 原因：新增页面，代码库中不存在
   - 后果：阻塞在调研阶段，无法开始编码
   - 对比：PR-02233（修改现有功能）5 分钟就定位到文件

**2. 准确率远低于预期**
   - 预期：≥ 95%
   - 实际：65%
   - 差距：30%
   - 原因：遗漏关键技术信息（页面位置、API 硬阻塞）

**3. Lite 模式在新增功能上的局限性**
   - 发现：修改现有功能 ✅ 快速高效
   - 发现：新增页面/模块 ❌ 信息不足
   - 结论：Lite 模式**不是万能的**，需要明确适用边界

### 优化建议

**1. 完善 Lite 模式指南**

**2. 调整适用场景说明**

## 适用性分析

**本需求是否适合 lite 模式**：**否**（不适合）

**理由**：
1. **新增页面类需求**：需要明确的页面位置信息（路由、菜单、文件结构）
   - 人工提炼时容易遗漏这些技术细节
   - Full extraction 会强制提取"页面在哪"

2. **API 强依赖需求**：无 API 就无法开始实现
   - Lite 模式只标记了"需要 API"，没有标记"硬阻塞"
   - Full extraction 会识别 API 依赖的严重性

3. **页面定位模糊**：原型图没有显示完整的路由或页面标识
   - 人工提炼无法从截图中推断出代码文件位置
   - Full extraction 会标记"信息不足"并要求补充

4. **复杂度高于预期**：
   - 预计 3-5 个文件 → 实际可能更多（新增页面 + 路由 + 菜单）
   - 双功能（配置页 + 列表列）→ 需要分别定位

**如果不适合，应该用什么模式**：
- **Full extraction** + 补充信息
- 或者**先获取完整信息**（页面位置、API 定义）后再用 lite 模式

## 经验总结

### 做得好的地方
1. **快速 Intake**：8 分钟完成人工提炼 + work-item 生成
2. **核心功能理解正确**：配置页 + 列表列的双功能识别准确
3. **边界条件提炼完整**：验证规则（档位不重复、区间连续、精度要求）都提炼到了
4. **及时发现问题**：15 分钟调研后立即识别阻塞，没有盲目编码

### 需要改进的地方

**1. Lite 模式提炼清单不够完善**
   - 当前清单：要做什么、影响哪些文件、如何验证、边界条件
   - **遗漏**：页面位置信息（路由、菜单、父页面）
   - **遗漏**：依赖严重性标记（可选 vs. 硬阻塞）

**2. 新增页面类需求的特殊性**
   - 修改现有功能：可以通过搜索快速定位文件
   - **新增页面**：必须知道"放在哪"（路由、菜单位置、文件结构）
   - Lite 模式没有针对"新增页面"的特殊提炼项

**3. 原型图信息提取不够系统**
   - 只看了"长什么样"（字段、交互）
   - **没看**：页面标题、路由、菜单位置、面包屑
   - Full extraction 会强制提取这些技术细节

**4. 复杂度评估偏乐观**
   - 预计 3-5 个文件
   - 实际：新增页面 + 路由 + 菜单 + API + 列表修改 → 可能 7-10 个文件
   - 没有考虑"新增页面"的脚手架成本

### 对未来 lite 模式的建议

**1. 增强提炼清单（针对新增页面）**
   ```
   ✅ 要做什么？
   ✅ 影响哪些文件？
   ✅ 如何验证？
   ✅ 边界条件？
   
   ➕ **新增**：如果是新增页面/组件
      - 页面/组件放在哪个目录下？
      - 路由是什么？
      - 挂在哪个菜单下？
      - 有没有参考页面/组件？
   
   ➕ **新增**：依赖严重性
      - API：可选 / 软依赖 / 硬阻塞
      - 设计稿：有 / 无 / 模糊
      - 其他前置条件
   ```

**2. 适用场景细化**
   - ✅ **适合 lite**：修改现有功能（文件可定位）
   - ✅ **适合 lite**：纯前端改动（无 API 依赖）
   - ✅ **适合 lite**：信息完整的小需求（< 3 文件）
   
   - ❌ **不适合 lite**：新增页面（缺少位置信息）
   - ❌ **不适合 lite**：API 强依赖且接口未定义
   - ❌ **不适合 lite**：原型图信息不完整（无路由、标题等）

**3. Lite 模式前置检查**
   在决定用 lite 模式前，先问：
   - [ ] 是修改现有功能吗？（还是新增页面/模块？）
   - [ ] 能否定位到目标文件？（搜索关键词能找到吗？）
   - [ ] API 依赖是否已就绪？（或者不依赖 API？）
   - [ ] 原型图/需求描述是否包含技术细节？（路由、菜单等）
   
   如果有任何一个"否"或"不确定" → 考虑 full extraction 或先补充信息

**4. 对比实验结论**
   
   | 实验 | 需求类型 | Lite 结果 | 结论 |
   |---|---|---|---|
   | PR-02233 | 修改现有功能 | ✅ 10分钟完成 | 适合 lite |
   | PR-02208 | 新增页面 + API 依赖 | ❌ 阻塞 | **不适合 lite** |
   
   **核心差异**：
   - 修改现有 → 文件可定位 → lite 快速
   - 新增页面 → 需要位置信息 → lite 遗漏 → 阻塞
