# **文档概述**

## **背景**

一期已完成预测市场核心交易链路：体育事件行情同步、市价买入/卖出、到期结算、资金冻结/解冻、5 分钟自动对账、链上钱包监控与 Web/App 前端。一期已具备“能跑通交易”的能力，但运营侧仍缺少数据可见性、收入可量化、异常可处置的工具。

二期目标是补齐运营与风控的“后台能力闭环”，让平台可观测（埋点\+统计）、可处置（事件管理\+手动平账）、可预警（告警配置），从而支撑规模化放量。三期面向商业化与体验升级。

## **二期范围一览**

|**模块**|**内容**|
|---|---|
|数据埋点|前端\+服务端双埋点，覆盖曝光、点击、下单漏斗、成交结果与结算，支撑转化分析与收入归因|
|每日收入统计|管理后台新增每日收入统计页（三类收入、成本、毛利）|
|事件管理|添加事件；上线/下线、开启/关闭交易；事件级三档 rate；多级分类|
|订单管理|管理后台新增订单列表页，对账用|
|仓位管理|管理后台新增仓位列表页（用户持仓维度）|
|手动平账|持仓不平时人工发起 FOK 平账，过程不产生新用户订单|
|告警配置|钱包余额告警、下单失败告警阈值与 Lark 通知渠道可配置化|



## **1\.3 目标与不做的事**

**二期做：运营可观测、可处置、可预警的后台工具。**

- 让运营/财务能看清订单与每日收入毛利。

- 让运营能手动控制事件可见性与可交易性。

- 让技术能在持仓不平时安全手动平账。

- 让告警阈值从硬编码变为后台可配置。

**二期不做：用户侧新交易玩法、限价单、自动补资、多语言法币结算、理财沉淀收益核算（列入三期候选）。**

**收入与成本口径**

**核心原则：所有金额按订单/成交逐笔记账后汇总，不按“成交额 × 比率”估算。其中 Polymarket 手续费必须取自每一笔链上成交回执返回的实际手续费逐笔累加，因其随成交价 p 非线性变化（见 3\.2），用估算会产生系统性偏差。**

|**项目**|**方向**|**口径（逐笔记账后汇总）**|
|---|---|---|
|买入加价收入<br>|收入<br>|Σ\_买入订单 \(单笔买入加价收入\)，按每笔买入订单累加|
|卖出抽水收入|收入|Σ\_卖出订单 \(单笔卖出抽水收入\)，链上卖出≤1U 的订单豁免不计|
|结算抽水收入|收入|Σ\_结算订单 \(结算抽水收入\)，统计盈利订单的结算抽水收入|
|Polymarket 手续费<br>|成本|Σ\_成交 fee\_actual：逐笔取链上成交回执返回的实际手续费累加，不按成交额估算（见 3\.2）<br>仅 taker 订单有手续费：<br>买入手续费 = 交易金额 × feeRate × \(1 \- 成交价\)<br>卖出手续费 = 卖出份额 × feeRate × 成交价 × \(1 \- 成交价\)|
|链上 Gas<br>（poly 目前免 gas，预留）|成本|Σ\_交易 实际 Gas\(POL\) 折算 USDT，逐笔累加|
|利润|结果|sum（买入加价收入\+卖出抽水收入\+结算抽水收入）|

*毛利计算逻辑：毛利 = \(Σ买入加价收入 \+ Σ卖出抽水收入 \+ Σ结算抽水收入\) 。各项均为“逐笔记账 → 按日/区间汇总”，PM手续费与 Gas 以链上回执/交易实际值为准，保证毛利可被财务逐笔复算、可审计对账。*

**参考资料：**

**Polymarket 手续费精确定义**

**结论：手续费不是固定的“0–2%”，而是 Polymarket 协议在撮合时按公式实时计算并只向 Taker（吃单方）收取。平台在链上是 Taker，故该费用计入平台成本。**

计算公式：fee = C × feeRate × p × \(1 − p\)，其中 C = 成交份额数量，p = 成交价格（0–1）。因此费用在 p=0\.5 时最高、向两端对称递减，与“成交价值×固定比例”不同。

*能否在成交结果中返回手续费：能。费用由协议在撮合时确定，成交回执/成交记录会返回该笔实际手续费。因此成本核算口径固定为：每笔链上成交完成时，将回执返回的实际手续费\(fee\_actual\)随该成交落库，按日/区间对 fee\_actual 逐笔累加得到 Polymarket 手续费总成本——不按“成交额 × 估算费率”计算。getClobMarketInfo\(conditionID\) 返回的 fd = \{ r: feeRate, e: exponent, to: takerOnly \} 仅用于下单前预估与展示，不作为入账依据；feesEnabled=false 的市场不收费。*

落库要求：成交/订单记录新增字段 pm\_fee\_actual（该笔实际手续费, USDC, 8位精度）与 fee\_tx\_hash（手续费所在成交哈希），作为收入统计与对账的唯一可信来源；埋点 polymarket\_buy\_result / polymarket\_sell\_result 的结果事件一并上报 pm\_fee\_actual。

**各类别 Taker 费率（来自 Polymarket 费用文档）**

|**市场类别**|**Taker feeRate**|**50% 价格时每100份费用**|**Maker 返利**|
|---|---|---|---|
|加密|0\.07|$1\.75|20%|
|体育|0\.03|$0\.75|25%|
|金融 / 政治 / 科技 / Mentions|0\.04|$1\.00|25%|
|经济 / 文化 / 天气 / 其他|0\.05|$1\.25|25%|
|地缘政治 / 世界事件|0|$0|—（零费用）|

*费用以 USDC 计、精度 5 位小数，最小 0\.00001 USDC，更小金额舍为 0。Maker 不收费。*

# **手动平账**

![Image](https://internal-api-drive-stream-sg.larksuite.com/space/api/box/stream/download/authcode/?code=YWRkNGRmNDUwYmJlMjE5NTk2ZGExOWE3ZmU1MDM5NTlfMjYwOGNlYzhiNzc2MDBhNzlkM2VkNDY1NmQxOTM2NjhfSUQ6NzY0OTc2ODI0MDAyOTE0Mjc1MV8xNzgxNjk5MDU3OjE3ODE3ODU0NTdfVjM)



1. 触发逻辑

    1. 5 分钟自动对账发现差异率 \> \{阈值\} 并触发 Lark 告警后，若差异无法自然消解，运营/技术在后台手动发起平账。平账过程不产生新的用户订单，仅调整平台钱包链上头寸。

2. 平账逻辑（以 Yes 为为例）

|**条件**|**动作**|
|---|---|
|交易所内份额 \> 链上份额|链上买入差额；买入份额=交易所−链上；价格=该事件卖一价|
|交易所内份额 \< 链上份额<br>|链上卖出差额；卖出份额=\|交易所−链上\|；价格=该事件买一价|

3. 平账逻辑

    - 挂单方式：盘口价市价单，直到达到目标份额停止。

    - 低于配置阈值的份额差异不执行平账。

    - NO 方向逻辑对称处理。

4. 操作流程

    11. 系统展示持仓差异列表：事件/方向、交易所持仓、链上持仓、差值、差异率、建议动作。

    12. 运营点击“平账”，弹窗展示动作、挂单价格、FOK 方式，二次确认。

    13. 执行后记录平账单（非用户订单）：操作人、动作、成交份额、哈希、结果。

    14. 平账完成后下一周期对账复核，差异率回落至阈值内则关闭告警。

5. 手动平账记录

    1. 新增手动平账记录，留痕“谁、在什么时间、做了什么、是否完成”，用于审计与复盘。

    2. 记录支持导出。

|**字段**|**说明**|
|---|---|
|平账单ID|唯一标识，非用户订单|
|事件 / 方向|平账目标事件与方向|
|动作|链上买入/卖出 \+ 份额|
|挂单价格|卖一价（买入）/ 买一价（卖出）|
|操作人|发起平账的运营/技术账号|
|发起时间|点击确认执行的时间|
|完成时间|平账成交完成时间（未完成为空）|
|结果 / 状态|执行中 / 已完成 / 失败（FOK 未成交，可重新发起）|

# **上线验收**

二期上线后按“灰度→功能验收→数据核对→稳定性观察→正式放量”五步推进，每一步设明确的通过标准（验收口径），任一项不达标即阻断进入下一步。

**上线方式与灰度**

- 先上预发/灰度：管理后台功能对内部运营/技术账号开放；前端用户侧按白名单或小流量（如 1%–5%）灰度。

- 灰度观察至少 1 个完整交易日（含一次自动对账与一次结算/卖出场景）后再扩量。

- 准备回滚预案：每个模块可独立开关（KV/配置），异常时单模块回退，不影响一期交易主链路。

**分模块验收清单**

|**模块**|**验收要点**|**通过标准**|
|---|---|---|
|数据埋点|各点位（polymarket\_\*）在真实操作下能上报，字段完整|下单漏斗 6 个点位齐全、关键字段\(uid/event\_id/amount/status\)无缺失，服务端结果事件与订单一致率 100%|
|每日收入统计|三类收入、PM手续费、Gas、毛利与账务一致|抽样 1 个交易日，页面毛利 = 财务口径误差为 0；PM手续费按成交回执实际值入账|
|事件管理|添加事件、上下线、开关交易、三档 rate、多级分类、比赛/事件判别|新增事件分类与 Polymarket 一致；关闭交易后前端不可买卖；rate 改动即时生效|
|订单管理|检索与字段、订单ID↔哈希对账|按 UID/订单ID/哈希均可检索；失败订单资金已退回现货账户|
|仓位管理|仓位字段与状态流转|建仓/加仓/平仓/结算后状态与保证金、份额正确|
|手动平账|FOK 平账、平账记录留痕|平账后差异率回落至阈值内；记录含操作人/时间/是否完成；不产生用户订单|
|告警配置|三类告警阈值可配、Lark 可达|改阈值后触发条件生效；测试告警 Lark 收到；持仓差异告警内容含四要素|



**端到端核对（资金与持仓）**

15. 持仓对账：连续 3 个自动对账周期，交易所内持仓总和 = 链上钱包持仓，差异率 \< 0\.1%。

16. 资金闭环：买入冻结、失败退回、卖出/结算入账金额与公式一致（精度 8 位，末位舍弃）。

17. 收入归集：买入加价/卖出抽水/结算抽水分别进入对应收入账户，合计 = 收入统计页数值。

18. 成本核对：PM手续费取自成交回执实际值、Gas 据实，毛利可被财务复算。

**稳定性与性能**

- 钱包监控每分钟、对账每 5 分钟稳定执行，无漏跑；告警无漏报/误报（误报率可接受阈值内）。

- 下单失败率、成交时延在目标范围；连续 3 次下单失败能正确触发暂停与告警。

- 后台列表页检索响应在可接受时延内（如 P95 \< 2s），大数据量分页正常。

**验收结论与放量**

各模块验收通过、端到端核对零差异、稳定性观察期无 P0/P1 缺陷后，由产品、技术、财务、运营四方会签确认，方可解除灰度、正式放量。验收过程与结论留档（验收报告）。

|**角色**|**验收职责**|
|---|---|
|产品|功能完整性、交互与文案、验收标准是否满足|
|技术|埋点/对账/告警链路、性能与回滚预案|
|财务|收入/成本/毛利口径与账务一致性|
|运营|事件管理、平账、告警处置流程可用性|

# **三期规划**

以下三期候选基于需求文档中标注的“待办/缺口/后期”项，以及二期落地后的自然延伸，按价值与依赖给出优先级建议，供评审筛选。

**候选清单与优先级**

|**方向**|**内容**|**来源**|**优先级**|
|---|---|---|---|
|自动补资|钱包余额触发紧急告警时自动从主钱包补充 USDC/POL，替代纯人工|文档8\.4|P0|
|差异化运营|加价率/抽水率从 KV 迁移到配置中心，按分类/事件/活动批量配置与灰度|文档5\.7|P0|
|多事件品类扩展|从仅体育扩展到加密、政治、金融等品类，行情接入与结算规则适配|文档4|P1|
|资金沉淀理财|USDT 余额沉淀理财收益核算与入账，纳入收入统计第四类|文档1\.2|P1|
|体验升级|事件搜索、自选/关注、价格走势图、持仓盈亏推送通知|前端延伸|P1|
|限价/条件单|在市价单基础上探索限价单（需评估链上撮合与风控）|规则延伸|P2|
|自动平账|小额差异自动 FOK 平账，保留人工审批兜底|二期延伸|P2|
|合规风控增强|额度分级、可疑交易监测、地区准入与 KYC 分层|文档9|P1|



**建议排期思路**

- P0 先行：自动补资 \+ 配置中心，直接降低运营人力与资金风险，依赖二期告警与事件管理已就绪。

- P1 并行：品类扩展与理财收益提升营收天花板；体验升级与合规增强提升留存与稳健性。

- P2 探索：限价单与自动平账技术复杂度高，放在体量验证后再投入。

**三期成功度量**

- 运营人力：补资/平账人工操作次数下降 ≥ 70%。

- 营收：非体育品类贡献收入占比 ≥ 30%；理财沉淀收益入账。

- 体验：下单漏斗买入成功转化率提升，持仓相关推送打开率达标。自动补资
