# Lite 模式操作指南

> docs_tdd v4.1 - 小需求快速通道

## 什么是 Lite 模式？

Lite 模式是一种跳过完整 PRD extraction 的快速开发流程，适用于需求清晰、影响范围小的场景。

**核心理念**：人工提炼 > AI extraction

**效率对比**（基于 2 个实验数据）：
- **时间**：10 分钟 vs. 20-25 分钟（节省 50-60%）✅ **适用场景下**
- **Token**：7K vs. 25-30K（节省 70-76%）✅
- **准确率**：65-100%（取决于需求类型）⚠️

**关键发现**：
- ✅ 修改现有功能：10 分钟完成，准确率 100%
- ❌ 新增页面/模块：容易遗漏关键信息，准确率降至 65%

---

## 一、适用场景判断

### ⚠️ 使用前必读：前置检查清单

在决定使用 lite 模式前，先回答以下问题：

- [ ] **是修改现有功能吗？**（还是新增页面/模块？）
- [ ] **能否快速定位到目标文件？**（搜索关键词能找到吗？）
- [ ] **API 依赖是否已就绪？**（或者不依赖 API？）
- [ ] **原型图/需求描述是否包含技术细节？**（路由、菜单位置等）

**决策规则**：
- ✅ 全部"是" → **适合 lite 模式**
- ⚠️ 有 1-2 个"否" → **谨慎使用**，补充信息后再开始
- ❌ 有 3+ 个"否" → **不适合 lite**，建议用 full extraction

---

### ✅ 适合 Lite 模式

**核心特征**：修改现有功能 + 影响范围小 + 信息完整

- ✅ **修改现有功能**（关键！）
  - 已有文件可定位
  - 已有组件可复用
  - 代码结构已知

- 需求描述清晰（截图 + 简短文字）
- 影响范围小（单页面、< 3 个文件）
- 技术方案明确（标准 UI 交互、简单逻辑）
- 快速验证类需求
- API 已就绪或纯前端改动

**示例**：
- 按钮添加 loading 效果 ✅
- 表单字段调整（已有表单）✅
- Toast 提示文案修改 ✅
- 简单的条件显示/隐藏 ✅
- 单个组件的样式调整 ✅
- 列表新增一列（已有列表）✅

### ❌ 不适合 Lite 模式

**核心特征**：新增页面/模块 + API 强依赖 + 信息不完整

- ❌ **新增页面/模块**（关键！）
  - 需要确定页面位置（路由、菜单、目录结构）
  - 需要创建文件脚手架
  - 人工提炼容易遗漏技术细节

- ❌ **API 强依赖且接口未定义**
  - 无 API 就无法开始实现
  - API 字段、类型、错误码等不明确

- ❌ **信息不完整**
  - 原型图缺少路由、标题、菜单位置
  - 需求描述模糊，需要反复确认

- 复杂业务逻辑（多端协同、复杂状态机）
- 高风险改动（支付、权限、数据迁移）
- 多文件协同（> 5 个文件）
- 需要完整追溯性的场景

**示例**：
- 新增配置页面 ❌（缺少页面位置信息）
- 新增列表页 ❌（需要路由、菜单、API）
- 新增模块/功能 ❌（影响范围大）
- 支付流程重构 ❌（高风险）
- 权限系统改造 ❌（复杂逻辑）
- API 接口未定义的功能 ❌（硬阻塞）

**为什么新增页面不适合？**（基于 PR-02208 实验）
1. 人工提炼时容易遗漏"页面放在哪"（路由、菜单、文件结构）
2. 无法通过搜索定位文件（因为还不存在）
3. 准确率从 100% 降至 65%
4. 导致实施阶段阻塞

## 二、操作步骤

### Step 1: 人工提炼（2-5 分钟）

**目标**：用 4-6 个要点描述清楚需求

**基础提炼要点**（所有需求）：

1. **要做什么？**
   - 核心功能/改动
   - 用户交互流程
   - 业务规则

2. **影响哪些文件/组件？**
   - 具体文件路径（如果知道）
   - 或页面/组件位置描述
   - 预估文件数量

3. **如何验证？**
   - 浏览器手动测试
   - 或自动化测试方法
   - 验收标准

4. **有什么边界条件？**
   - 特殊情况处理
   - 错误处理
   - 兼容性要求

**⚠️ 新增页面/组件专项**（如果是新增功能，必须回答）：

5. **【新增页面】页面/组件放在哪？**
   - 路由是什么？（如 `/future/api-rate-config`）
   - 挂在哪个菜单下？（如：合约配置 → API费率配置）
   - 目录结构？（如 `apps/futures-admin/src/pages/ApiRateConfig/`）
   - 有没有参考页面？（如：类似 `RebateLevelConfig`）

6. **【API 依赖】依赖严重性？**
   - ✅ 纯前端（无 API 依赖）
   - ⚠️ 软依赖（有 mock 数据可以先实现界面）
   - ❌ 硬阻塞（无 API 就无法开始实现）
   
   如果是硬阻塞：
   - API 接口定义在哪？（文档链接、Swagger、口头确认）
   - API 是否已开发完成？
   - 缺什么信息会阻塞？

**示例 1**（修改现有功能 - 修改密码按钮 loading）：
```
1. 要做什么？
   - 修改登录密码页面，点击"确定"按钮后显示 loading 并禁用按钮

2. 影响哪些文件？
   - apps/admin/src/apps/ChangePassword/index.tsx
   - 预计 1 个文件

3. 如何验证？
   - 浏览器测试：点击按钮 → 看到 loading → 按钮不可再点 → API 返回后恢复

4. 边界条件？
   - API 成功：页面跳转或提示
   - API 失败：按钮恢复 + 错误提示

5. 新增页面？
   - 否，修改现有页面

6. API 依赖？
   - 纯前端改动（API 已存在）
```

**示例 2**（新增页面 - API动态费率配置）：
```
1. 要做什么？
   - 新增"API动态费率配置"页面，展示 L1-L5 五个档位的配置表格
   - 支持编辑每个档位的配置并保存

2. 影响哪些文件？
   - 新增页面组件
   - 路由配置
   - 菜单配置
   - 预计 3-5 个文件

3. 如何验证？
   - 浏览器测试：菜单存在 → 点击进入 → 看到表格 → 编辑并保存成功

4. 边界条件？
   - L1-L5 档位不可重复
   - 成交量区间必须连续
   - 费率精度验证

5. 【关键】新增页面放在哪？
   - ❌ **缺失信息** - 不知道路由是什么
   - ❌ **缺失信息** - 不知道挂在哪个菜单下
   - ❌ **缺失信息** - 不知道放在哪个目录
   - ⚠️ **无法继续** - 需要补充页面位置信息

6. 【关键】API 依赖？
   - ❌ **硬阻塞** - 无 API 就无法实现
   - ❌ **缺失信息** - API 接口定义不明确
   - ⚠️ **无法继续** - 需要先获取 API 接口定义

→ 结论：此需求**不适合 lite 模式**，需要先补充信息
```

### Step 2: 生成 Work-Item（1-2 分钟）

**2.1 复制模板**
```bash
cp common/templates/lite-work-item-template.json prds/PR-XXXXX/work-item.json
```

**2.2 填充内容**

打开 `prds/PR-XXXXX/work-item.json`，修改以下字段：

1. **projectId**：`"PR-XXXXX"` → 实际项目 ID

2. **requirements**：根据人工提炼填充
   ```json
   {
     "requirementId": "R-001",
     "statement": "修改登录密码页面的'确定'按钮，点击后立即显示 loading 状态并禁用按钮...",
     "affectedSurfaces": [
       {
         "surfaceId": "S-001",
         "locator": "apps/admin/src/apps/ChangePassword/index.tsx - 确定按钮",
         "disposition": "implement"
       }
     ],
     "evidencePlan": [
       {
         "type": "manual-browser",
         "description": "浏览器测试：点击按钮 → loading → 禁用 → 恢复"
       }
     ]
   }
   ```

3. **时间戳**：更新 `completedAt` 和 `lastCheckpointAt` 为当前时间

**2.3 创建人工输入记录**

创建 `prds/PR-XXXXX/human-input.md`：
```markdown
# PR-XXXXX 人工提炼

**提炼时间**：2026-09-23
**提炼人**：[你的名字]

## 需求概述
[一句话描述]

## 提炼要点
1. 要做什么？
   [...]

2. 影响哪些文件？
   [...]

3. 如何验证？
   [...]

4. 边界条件？
   [...]

## 参考资料
- 截图：[路径]
- 原始需求：[路径或链接]
```

### Step 3: 实施（正常流程）

按照 work-item 的 requirements 正常开发，无需特殊处理。

### Step 4: 记录数据（可选）

如果想为 lite 模式收集数据，使用实验记录模板：
```bash
cp common/templates/lite-experiment-template.md prds/PR-XXXXX/lite-experiment-log.md
```

记录：
- 人工提炼时间
- 生成 work-item 时间
- 实施时间
- Token 消耗（如果可以统计）
- 准确率（是否需要返工）

## 三、常见问题

### Q1: 如何判断是否适合 lite 模式？

**简单判断法**：
- 你能在 3 分钟内说清楚"要做什么"吗？✅ → 适合
- **是修改现有功能吗？**（不是新增页面）✅ → 适合
- 影响 < 3 个文件吗？✅ → 适合
- 需求有截图或清晰描述吗？✅ → 适合
- 是高风险改动吗？❌ → 不适合
- **是新增页面吗？**❌ → **不适合**

**关键区分**：修改 vs. 新增
- **修改现有功能**：文件可定位 → ✅ 适合 lite
- **新增页面/模块**：需要页面位置信息 → ❌ 不适合 lite

### Q2: lite 模式会不会遗漏需求？

**数据**（基于 2 个实验）：
- 修改现有功能：准确率 100% ✅
- 新增页面/模块：准确率 65% ❌（容易遗漏页面位置信息）

**原因**：
- ✅ 人工理解通常比 AI extraction 更准确（对于熟悉的改动）
- ✅ 对于小需求，人工可以快速抓住核心
- ❌ 但对于新增功能，容易遗漏技术细节（路由、菜单、文件结构）

**建议**：
- 如果需求复杂或模糊 → 不要用 lite 模式
- **如果是新增页面 → 不要用 lite 模式**（除非已有完整的页面位置信息）
- 如果不确定是否遗漏 → 让同事 review 人工提炼

### Q3: 为什么新增页面不适合 lite 模式？

**实验发现**（PR-02208）：
1. 人工提炼时只关注"做什么"，忽略"放在哪"
2. 原型图通常不包含路由、菜单位置等技术细节
3. 导致实施时无法定位目标文件，阻塞 15+ 分钟
4. 准确率从 100% 降至 65%

**新增页面需要的信息**：
- 路由定义（如 `/future/api-rate-config`）
- 菜单位置（如：合约配置 → API费率配置）
- 文件目录（如 `apps/futures-admin/src/pages/ApiRateConfig/`）
- 参考页面（如：类似 `RebateLevelConfig`）

**解决方案**：
- 选项 1：先获取完整信息（路由、菜单），再用 lite 模式
- 选项 2：用 full extraction（会强制提取页面位置信息）

### Q4: lite 模式和 full extraction 可以混用吗？

**可以，而且推荐**。

- 小需求 + 修改现有功能 → ✅ lite 模式
- 新增页面/模块 → ❌ full extraction
- 复杂需求 → ❌ full extraction
- 根据场景灵活选择

**决策表**：

| 需求类型 | 推荐模式 | 理由 |
|---|---|---|
| 修改现有按钮/字段 | Lite | 快速、准确率高 |
| 列表新增一列（已有列表） | Lite | 文件可定位 |
| 新增配置页面 | Full | 需要页面位置信息 |
| 新增列表页 | Full | 需要路由、菜单、API |
| API 接口未定义 | Full 或等待 | 硬阻塞 |

### Q5: 如果实施时发现需求理解错了怎么办？

**正常流程**：
1. 停止实施
2. 回看原始需求（human-input.md 有记录）
3. 更新 work-item 的 requirements
4. 继续实施

**不影响**：lite 模式的 work-item 也是可追溯、可修改的。

## 四、最佳实践

### 1. 人工提炼时

- ✅ 写清楚"要做什么"，不要假设 AI 能补全
- ✅ 尽量写具体的文件路径或组件名
- ✅ 列出明确的验收标准
- ❌ 不要复制粘贴 PRD 原文（lite 模式的目的就是提炼）

### 2. 生成 work-item 时

- ✅ 用模板，不要从零开始写
- ✅ requirements 可以有多个（如果有多个子需求）
- ✅ 每个 requirement 对应明确的 affectedSurfaces
- ❌ 不要省略 evidencePlan（验证很重要）

### 3. 实施时

- ✅ 按照 requirements 逐条实现
- ✅ 如果发现遗漏，立即更新 work-item
- ✅ 记录实际修改的文件（changedPaths）
- ❌ 不要偏离 requirements（如果要改，先更新 work-item）

### 4. 验证时

- ✅ 按照 evidencePlan 逐条验证
- ✅ 覆盖边界条件
- ✅ 如果失败，记录原因
- ❌ 不要跳过验证（即使是小需求）

## 五、实验数据对比

### 实验 1: PR-02233-BTN-LOADING（修改现有功能）

**需求**：修改登录密码页面按钮 loading 效果

**特征**：
- 修改现有功能 ✅
- 1 个文件
- 纯前端改动
- 信息完整

**结果**：
- Intake：3 分钟（2min 提炼 + 1min 生成 work-item）
- 实现：7 分钟（包含验证）
- 总时间：10 分钟
- Token：7K
- 准确率：100%
- **状态：完成** ✅

**对比 full extraction**：
- 节省时间：50-60%（10min vs. 20-25min）
- 节省 token：76%（7K vs. 30K）
- 准确率：相同（100%）

**结论**：**Lite 模式非常适合此类需求**

---

### 实验 2: PR-02208（新增页面 + API 依赖）

**需求**：合约配置新增"API动态费率配置"页面

**特征**：
- 新增页面 ❌
- 3-5 个文件
- API 强依赖 ❌
- 信息不完整 ❌

**结果**：
- Intake：8 分钟（6min 提炼 + 2min 生成 work-item）
- 实现：15 分钟调研后阻塞
- 总时间：23 分钟（未完成）
- Token：7K
- 准确率：65%（遗漏页面位置信息、API 硬阻塞标记）
- **状态：阻塞** ❌

**阻塞原因**：
1. 人工提炼遗漏"页面放在哪"（路由、菜单、目录）
2. 无法定位目标文件（因为还不存在）
3. API 接口未定义（硬阻塞）

**结论**：**Lite 模式不适合此类需求**

### 关键差异总结

| 维度 | 实验 1（修改现有） | 实验 2（新增页面） |
|---|---|---|
| 需求类型 | 修改现有功能 | 新增页面 + API 依赖 |
| 文件可定位 | ✅ 是 | ❌ 否 |
| 信息完整性 | ✅ 完整 | ❌ 缺少页面位置 |
| Intake 时间 | 3 分钟 | 8 分钟 |

| 准确率 | 100% | 65% |
| 结果 | ✅ 完成 | ❌ 阻塞 |
| **Lite 模式适用** | ✅ **是** | ❌ **否** |

**核心发现**：
- Lite 模式在"修改现有功能"场景下表现优秀
- Lite 模式在"新增页面/模块"场景下容易失败
- 准确率差异：35%（100% vs. 65%）
